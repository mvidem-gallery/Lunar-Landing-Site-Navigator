# Lunar Horizon — Модуль планування місячної місії

Lunar Horizon оцінює освітлення та пряму видимість Землі в заданій точці посадки протягом місячної місії. Модуль поєднує карти висот LOLA і SLDEM2015 з ефемеридами NASA/JPL Horizons, щоб визначати положення Сонця й Землі відносно місцевого горизонту.

## Вхідні дані

| Поле | Що передавати | Формат і межі |
| --- | --- | --- |
| `lat` | Широта посадки | Планетоцентрична широта в системі MOON_ME, від −90 до 90°. Південь зі знаком мінус. |
| `lon` | Довгота посадки | Десяткові градуси від −180 до 180. Схід зі знаком плюс, захід зі знаком мінус. |
| `start` | Дата й час посадки | UTC. Формат у URL без суфікса Z. YYYY-MM-DDTHH:mm |
| `end` | Дата й час завершення місії | Той самий формат. Пізніше за start. До 365 діб між початком і кінцем. Роки 2000–2100. |
| `darkLimit` | Запас роботи без прямого світла підряд | Від 0 до 365 діб. Дробове число дозволено, наприклад 2.5 для 60 годин. Типово 3 доби. |
| `height` | Висота точки спостереження над рельєфом | Від 0.1 до 100 м. Типово 1.7 м. Використовується в розрахунку горизонту. |

**Крок ефемерид.** Доступні 1, 10, 30 і 60 хвилин. Типове значення — 10 хвилин. Для довгих місій крок може автоматично збільшитися.

## Перегляд місії

Сторінка показує рельєф, посадковий апарат, Сонце та Землю в інтерактивній 3D-сцені. Шкала часу обмежена датами місії. У повноекранному режимі доступні повзунки часу й підйому камери до 10 км. Підйом камери змінює лише ракурс.

## Результати для користувача

| Результат | Що показує модуль |
| --- | --- |
| Оцінка дат | Чи вкладається найдовший безперервний період без прямого світла в запас роботи апарата. |
| Найдовший період без світла | Початок, кінець у UTC і тривалість у годинах та добах. |
| Найдовший період без видимості Землі | Початок, кінець у UTC і тривалість. Геометрична оцінка можливості прямого зв’язку. |
| Найближче придатне вікно | Якщо ліміт перевищено, модуль шукає найраніший пізніший початок місії тієї самої тривалості, до 365 діб від початкової дати. Показує нові дати та найдовший період без світла. |
| Підсумки місії | Тривалість і частка часу з прямим світлом, із видимістю Землі та з обома умовами одночасно. |
| Дані на вибраний момент | Азимут і висота Сонця й Землі, кут падіння світла до нормалі схилу, статуси освітлення та видимості, відстань до Землі й затримка сигналу в один бік і туди-назад. |

Пошук вікна враховує запас роботи без світла. Якщо видимість Землі теж має бути умовою, інтеграції потрібен окремий ліміт безперервної втрати видимості. Фактичний радіозв’язок залежить також від станції, антени й параметрів сигналу.

## Інтеграція з головним проєктом

**Уже працює.** URL приймає lat, lon, start, end і height. Сторінка заповнює форму й автоматично запускає розрахунок. Ліміт darkLimit задається у формі. Підсумок відображається на сторінці, відліки за часом можна експортувати в CSV.

**Потрібно додати.** Додати прийом darkLimit через URL і структуровану відповідь. Окремого API для підсумку наразі немає.

**Поля відповіді.** darknessLimitMet — результат перевірки. longestDarkness і longestEarthOutage — межі в UTC та тривалість у секундах. recommendedWindow і windowSearchStatus — дати, максимальна тривалість тіні та статус пошуку. totals — тривалості в секундах. effectiveStepMinutes і demSpacingMeters — фактичний крок розрахунку та крок сітки рельєфу біля посадки.

**Точність.** Моменти переходів оцінюються між відліками, тому дуже короткі події можуть бути пропущені.

## Як проходить розрахунок

1. `app.js` читає параметри, перевіряє поля й уточнює крок ефемерид. У поточній версії розрахунок запускається після завантаження базових карт.
2. Сервер видає підмножини детальних карт для вибраної ділянки. Воркер об’єднує їх із локальними картами, обчислює висоту посадки та профіль горизонту на відстані до 250 км.
3. Браузер запитує ефемериди для введених дат. Висота для цього запиту обчислюється як `alt = (groundElevationMeters + height) / 1000`. Поле `height` у формі задається в метрах над рельєфом, а `alt` для ефемерид — у кілометрах відносно опорної сфери Місяця.
4. `app.js` і `mission.js` зіставляють ефемериди з профілем горизонту та будують часові інтервали. За потреби окремий запит майбутніх ефемерид Сонця запускає пошук нового вікна.
5. 3D-сцена отримує геометрію та додатковий шар орбітальних знімків. Підсумок місії обчислюється за картою висот і ефемеридами. Фото, оглядове освітлення та висота камери керують відображенням.

За прямого освітлення центр Сонця перебуває над горизонтом рельєфу, а кут променів до нормалі схилу менший за 90°. Для видимості Землі перевіряється центр її диска. Поточна оцінка запасу припускає заряджений апарат на момент посадки та відновлення запасу після повернення прямого світла. Часткову видимість дисків і затемнення модель не враховує.

## Серверні маршрути

| Метод і маршрут | Параметри | Відповідь |
| --- | --- | --- |
| `GET /api/ephemeris` | `lat`, `lon`, `alt` у км, `start` і `end` у форматі ISO 8601 з UTC, `step` у хвилинах. Для пошуку вікна можна передати `target=sun`. | JSON із масивами `sun` і `earth`, фактичним `step` та системою координат. Один відлік має вигляд `[utcEpochMs, azimuthDeg, elevationDeg, angularDiameterDeg, distanceKm]`. |
| `GET /api/terrain-detail` | `lat`, `lon`, необов’язковий `detail=fine`, `landing` або `stereo`. Без `detail` повертається регіональна сітка. | Двійкові висоти. `X-LOLA-Grid` задає початковий рядок, стовпець, розмір і, якщо вказано, щільність. LOLA кодується як little-endian Int16 з кроком 0,5 м. `X-DEM-Format: float32-km` позначає SLDEM2015 у кілометрах. `204` означає відсутність шару для точки. |
| `GET /api/imagery` | Номер плитки `x`, `y`, масштаб `z`, проєкція `EQ`, `NP` або `SP`. | JPEG для екваторіальної проєкції, PNG для полярної. Знімки потрібні для 3D-перегляду. |

Базові карти браузер отримує через `/global-dem.bin`, `/terrain.json`, `/far.json`, `/terrain.packed` і `/far.packed`. Роути `.packed` генеруються з даних у `data/`. За збою детальних карт застосовується нижча доступна роздільність. За збою JPL розрахунок для нових параметрів не виконується, а інтерфейс може показати попередній успішний результат із повідомленням.

## Варіанти об’єднання

### Окрема сторінка в єдиному проєкті

Найменше змін потребує окремий маршрут або піддомен, де Lunar Horizon зберігає власну сторінку й серверні маршрути. Головний проєкт передає введені параметри посиланням. Наприклад, відносний URL сторінки модуля:

```text
/?lat=-89.45&lon=30&start=2026-11-14T00:00&end=2026-11-21T00:00&height=1.7
```

Для монтажу під `/lunar/` потрібно змінити або проксувати **всі** абсолютні шляхи модуля. Зараз HTML, JavaScript-імпорти, Web Worker, дані висот і `/api/*` звертаються від кореня домену. Узгодити базовий шлях треба також у збірці, сервері й посиланні на головну сторінку. Інакше роути на зразок `/app.js` або `/api/ephemeris` можуть перетнутися з іншими модулями.

Якщо 3D-вид вбудовують через iframe, модуль має лишатися доступним для користувача за правилами хостингу. Для системного повноекранного режиму iframe потрібен дозвіл `allowfullscreen`. Передавання підсумку в батьківську сторінку через `postMessage` потребує окремої реалізації з перевіркою дозволених джерел.

### Спільний інтерфейс і дані

Якщо головний проєкт сам показує підсумок, винесіть формування результату з функцій `analyze()` та `assessMission()` у функцію, яка повертає дані. Вона має використати ті самі обчислення з `mission.js` і той самий профіль горизонту. Далі можна підключити цю функцію в спільний клієнт або зробити окремий JSON-маршрут. Поточний `/api/ephemeris` повертає положення небесних тіл. Для оцінки місії додатково потрібен рельєф.

Для JSON домовтеся про такі правила:

| Частина контракту | Рекомендований формат |
| --- | --- |
| Вхід | `lat`, `lon`, `height`, `darkLimit` як числа, `start` і `end` як ISO 8601 з `Z`. За потреби `stepMinutes` і спільний ідентифікатор місії. |
| Межі інтервалів | `startUtc`, `endUtc`, `durationSeconds`. Якщо події не було, тривалість дорівнює нулю, а межі можуть бути `null`. |
| Пошук вікна | `recommendedWindow: null`, поки вікно відсутнє. `windowSearchStatus` розрізняє `not_required`, `searching`, `found`, `not_found` та `error`. |
| Підсумок | `totals.sunlightSeconds`, `totals.earthVisibleSeconds` і `totals.bothAvailableSeconds`. Частки можна отримати діленням на тривалість місії. |
| Якість і помилки | Повертати фактичний крок, джерело або роздільність карти біля посадки та ознаку резервного шару. Помилку завантаження передавати окремо від результату, за яким умова місії не виконана. |

Пошук вікна виконується після розрахунку вибраних дат, тому для спільного інтерфейсу корисно окремо показувати статус основного розрахунку і статус пошуку. У CSV містяться часові відліки, а машинозчитуваний підсумок варто повертати окремо.

## Запуск і перевірка після об’єднання

- **Локальний запуск.** У корені модуля з Node.js 22 або новішим виконати `npm run dev`. Типовий порт — 3000. Налаштувати інший можна через `PORT` або командою `npm run dev -- --port 3100`. Three.js уже в архіві. Для 3D потрібен WebGL 2.
- **Сервер.** Локальний режим використовує Node HTTP, а `npm run build` створює Worker ESM у `dist/server/index.js`. На іншому хостингу обробники з `src/server.js` можна підключити до його роутера. Просте статичне розміщення не обслуговуватиме ці API. `.openai/hosting.json` містить ідентифікатор чинного сайту, для нового деплою потрібна конфігурація спільного проєкту.
- **Доступ до джерел.** Серверу потрібен вихід до JPL Horizons, архівів висот NASA PDS і SLDEM2015 та NASA Moon Trek. Серверні запити висот використовують HTTP Range. Для різних доменів краще проксувати запити через той самий origin. Якщо потрібен прямий міждоменний доступ, налаштувати CORS і відкрити клієнту заголовки `X-LOLA-Grid` та `X-DEM-Format`.
- **Перевірка.** Запустити `npm test`, а після збірки — `node scripts/validate-artifact.mjs`. В об’єднаному застосунку перевірити початкові поля, завантаження Web Worker і всіх карт, одну полярну та одну неполярну точку, довгу місію, підбір альтернативного вікна і поведінку за збою зовнішніх даних. Зіставити підсумки та CSV з окремим сайтом за однакових вхідних параметрів.
